# 工作流协调机制

## 问题本质

三个系统各有自己的状态流转：

```
Multica 的 Issue 生命周期：
  todo → in_progress → in_review → done

OpenSpec 的 Change 生命周期：
  explore → propose → apply → verify → archive

Superpowers 的 Skill 触发链：
  brainstorming → writing-plans → git-worktrees → executing-plans/TDD → code-review → finishing-branch
```

如果不做协调，Agent 会遇到：
- Builder 拿到 issue 后，Superpowers 触发 `brainstorming`，但 OpenSpec 已经有完整设计 → 冲突
- Builder 的 Superpowers 触发 `writing-plans`，要生成新计划 → 但 OpenSpec 已经有 tasks.md → 重复
- Builder 不知道 Multica issue 状态该怎么流转 → 混乱

## 核心原则

> **OpenSpec 管"做什么"，Superpowers 管"怎么做"，Multica 管"谁来做、做到哪了"。**

三者不冲突，只是管的层次不同。关键是**根据角色和阶段，决定哪些 Superpowers skill 触发、哪些跳过**。

## 三个系统的角色分工

```
┌─────────────────────────────────────────────────────────────────┐
│                         Multica                                  │
│  职责：协调（Who + When + Status）                                │
│  ──────────────────────────────────────────────────────────────  │
│  · Issue 状态流转：todo → in_progress → in_review → done        │
│  · 任务分配：谁来做                                              │
│  · 进度追踪：做到哪了                                            │
│  · 不关心具体的 spec 内容和代码实现方式                            │
├─────────────────────────────────────────────────────────────────┤
│                        OpenSpec                                   │
│  职责：规划（What + Why + Scope）                                 │
│  ──────────────────────────────────────────────────────────────  │
│  · Spec 定义：系统应该做什么                                      │
│  · Change 管理：每个变更的 proposal/specs/design/tasks            │
│  · 归档：变更完成后 specs 合入主规格                               │
│  · 不关心谁来做、怎么做                                          │
├─────────────────────────────────────────────────────────────────┤
│                      Superpowers                                  │
│  职责：执行（How + Quality）                                      │
│  ──────────────────────────────────────────────────────────────  │
│  · 代码质量：TDD、code review、systematic debugging               │
│  · 分支管理：worktree 隔离、branch finishing                      │
│  · 子代理调度：subagent-driven-development                        │
│  · 不关心 spec 怎么组织、issue 怎么分配                           │
└─────────────────────────────────────────────────────────────────┘
```

## 每个角色的 Superpowers Skill 触发规则

### Spendly-Architect

Architect 同时使用 OpenSpec 和 Superpowers，但**不同阶段激活不同 skill**：

```
阶段              OpenSpec 操作        Superpowers Skill           说明
─────────────────────────────────────────────────────────────────────────
探索              /opsx:explore        brainstorming ✅            允许触发
                                          (Architectural 路径)

设计              /opsx:propose        brainstorming ✅            设计阶段
                                          (Architectural 路径)      人工审批是必要的
                                     writing-plans ✅              为 tasks.md 提供输入

执行（派发）      /opsx:apply          不触发 ❌                    代码由 Builder 写
                                     （由 Builder 执行）

审查              ─                    requesting-code-review ✅   对 Builder 的代码做 review

验证              /opsx:verify         verification-before-        验证实现与 spec 一致
                                          completion ✅

归档              /opsx:archive        finishing-a-development-     合并到 main
                                          branch ✅
```

**关键规则：**
- Architect 在**探索和设计阶段**完全拥抱 Superpowers 的 brainstorming 流程
- brainstorming 的输出直接成为 OpenSpec 的 proposal + specs + design
- Architect **不写功能代码**，所以不触发 executing-plans / TDD

### Spendly-Builder

Builder 使用 Superpowers 的**执行类 skill**，但**跳过规划类 skill**：

```
阶段              OpenSpec 上下文       Superpowers Skill           触发？
─────────────────────────────────────────────────────────────────────────
接单              读取 change artifacts  不触发                      先读上下文
                  (proposal/specs/
                   design/tasks)

规划              ─                    brainstorming ❌ 跳过         OpenSpec 已有设计
                                     writing-plans ❌ 跳过         OpenSpec 已有 tasks.md

分支              ─                    using-git-worktrees ✅       创建隔离工作空间
                                                                          （如果需要）

执行              按 tasks.md 逐项      executing-plans ✅           tasks.md 就是 plan
                  勾选完成              或
                                     subagent-driven-dev ✅        如果支持子代理

编码              ─                    test-driven-development ✅   RED-GREEN-REFACTOR

自审              ─                    requesting-code-review ✅    每完成一个 task 自审

完成              在 tasks.md 勾选      finishing-a-development-     汇报完成
                  所有项                 branch ✅
```

**关键规则：**
- Builder 的指令中必须明确：**跳过 brainstorming 和 writing-plans**
- 原因：OpenSpec 的 artifacts 已经完成了规划工作
- `tasks.md` 就是 Superpowers 所说的 "implementation plan"
- Builder 从 `executing-plans` 或 `subagent-driven-development` 开始

### Spendly-QA

QA 只使用 Superpowers 的**验证类 skill**：

```
阶段              上下文                Superpowers Skill           触发？
─────────────────────────────────────────────────────────────────────────
接单              读取 specs +           不触发                      先读上下文
                  Builder 的测试

规划              ─                    brainstorming ❌ 跳过         任务由 Architect 指定
                                     writing-plans ❌ 跳过         不需要计划文档

执行              写测试               test-driven-development ✅   测试本身遵循 TDD
                                     systematic-debugging ✅       如果发现 bug 需要定位

验证              ─                    verification-before-         确认测试覆盖完整
                                          completion ✅

完成              ─                    finishing-a-development-     汇报完成
                                          branch ✅
```

## Bug-Fix 循环机制

QA 测试发现 bug 后，进入 QA ↔ Builder 的修复循环。Architect 不参与循环内部，只在循环结束后做最终 review。

### 循环流程

```
QA 测试
  │
  ├── 通过 → 汇报"验证通过" → 进入 Architect 最终 review
  │
  └── 发现 bug
        │
        ▼
      QA 在 issue 评论中 @Builder 报告 bug
        │
        ▼
      Builder 修复（Multica 触发新 task）
        │
        ▼
      Builder commit + @QA 汇报修复内容
        │
        ▼
      QA 重新测试 ──→ 回到循环顶部
```

### 循环次数限制

| 轮次 | 处理方式 |
|------|---------|
| 第 1-2 轮 | 正常循环。QA 报 bug → Builder 修复 → QA 重测 |
| 第 3 轮 | **升级给 Architect**。QA 评论"@Architect 第 3 轮仍有未解决的问题，需要你介入" |
| 第 3 轮之后 | Architect 介入判断：spec 问题 / design 问题 / 实现问题 |

### 为什么限制 3 轮

- **第 1 轮**：正常的边界 case 遗漏，Builder 自己能修
- **第 2 轮**：可能有更深层问题，但仍在 Builder 能力范围内
- **第 3 轮**：反复修不好 → 通常是 spec 不清晰、design 有缺陷、或 Builder 误解了需求
- 超过 3 轮需要 Architect 从 spec 和 design 层面重新审视

### 升级后 Architect 的介入方式

| 判断 | 操作 |
|------|------|
| spec 不清晰 | 更新 openspec/specs/ 中的规格，补充缺失的 scenario |
| design 有缺陷 | 更新 design.md，调整技术方案 |
| 实现有根本性问题 | 重新派发给 Builder，补充更详细的上下文 |

## Multica Issue 状态与工作流的映射

### 状态流转规则

```
todo ─────────── Architect 创建 change，分配给小队
  │
  │  Architect 派发任务给 Builder
  ▼
in_progress ──── Builder 开始实现
  │              QA 补充测试
  │              全程保持 in_progress
  │
  │  所有 tasks 完成 + QA 通过 + Architect review 通过
  ▼
in_review ────── Architect 运行 /opsx:verify
  │              等待人工最终确认（如果需要）
  │
  │  确认通过
  ▼
done ─────────── /opsx:archive
                 feature 分支合并到 main
                 删除 feature 分支
```

### 谁负责更新状态

| 状态变更 | 由谁操作 | 触发时机 |
|---------|---------|---------|
| → `todo` | Architect | 创建 change 并分配 |
| → `in_progress` | Leader（Architect） | 首次派发任务时 |
| 保持 `in_progress` | — | Builder/QA 工作期间 |
| → `in_review` | Architect | 所有任务完成 + review 通过 |
| → `done` | Architect | /opsx:archive 完成后 |

**重要：**
- Builder 和 QA **不要**自行修改 issue 状态
- Builder 完成后在评论中汇报，等 Architect 审查
- issue 状态和 Multica task 状态是**分开的**：task 完成 ≠ issue 完成

## Superpowers 的 brainstorming 与 OpenSpec 的关系

这是最容易混淆的部分。具体说明：

### 什么时候 brainstorming 真正需要

| 场景 | brainstorming？ | 说明 |
|------|----------------|------|
| 全新功能的初始设计 | ✅ 需要 | brainstorming → 输出变成 OpenSpec proposal |
| 已有 change，Builder 要实现 | ❌ 不需要 | OpenSpec artifacts 就是设计 |
| 实现中发现需要小的架构调整 | ✅ 需要 | Bounded 路径，快速决策 |
| 实现中遇到技术细节问题 | ❌ 不需要 | 直接查 design.md 或问 Architect |

### brainstorming 的输出去向

```
Architect 做 brainstorming
      │
      ▼
brainstorming 的输出（设计决策）
      │
      ├──→ proposal.md   （为什么做、做什么）
      ├──→ specs/         （行为规格）
      ├──→ design.md      （技术方案）
      └──→ tasks.md       （实现任务）
           │
           │ 这些就是 OpenSpec 的 artifacts
           │
           ▼
      Builder 拿到后直接执行
      （不再 brainstorming）
```

## 常见问题

### Q: Builder 的 Superpowers 自动触发了 brainstorming 怎么办？

A: 在 Builder 的指令中已经明确写了"跳过 brainstorming"。Superpowers 的 skill 触发虽然自动，但指令中的明确规则优先级更高。如果仍然触发，Builder 应该说："OpenSpec artifacts 已存在，跳过 brainstorming，直接进入执行。"

### Q: Builder 的 Superpowers 自动触发了 writing-plans 怎么办？

A: 同上。Builder 应该说："tasks.md 已经是完整的实现计划，跳过 writing-plans。将 tasks.md 作为 plan 直接执行。"

### Q: 如果实现中发现 design.md 有错误怎么办？

A: Builder 在 issue 评论中通知 Architect，描述具体问题。Architect 决定是否更新 design.md。不要自行修改 OpenSpec artifacts。

### Q: 如果 tasks.md 中的任务描述不够详细怎么办？

A: Builder 在 issue 评论中要求 Architect 补充细节。或者，如果 Architect 的指令允许，Builder 可以在实现前细化自己的本地 task notes，但不修改 openspec/changes/ 中的原始文件。

### Q: Superpowers 的 TDD 和 OpenSpec 的 verify 有什么区别？

A: 不同层次：
- **TDD**：代码级别的测试驱动（写一个测试 → 写最少代码 → 通过 → 重构）
- **/opsx:verify**：变更级别的验证（所有 requirements 是否实现、所有 scenarios 是否覆盖、design 是否一致）

TDD 确保每行代码正确，verify 确保整体变更完整。两者互补。
